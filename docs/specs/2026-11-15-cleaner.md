# MIA: the cleaner — Spec

**Status:** v0.1 · 2026-11-15 · draft for the user's approval; nothing here is built. Rests on the branch
`round-fixes` (a round's wait on autodev is timed; autodev says a stop with the `needs-human` label). §8 lists
the decisions that are the user's; each has a default the rest of the spec assumes.

## 1. Intent

Rounds keep ending up somewhere they cannot leave by themselves: reading "in progress" with nothing running,
or stopped for a reason that has since passed, or leaving a job, an issue or a pull request behind. Each time
a person noticed hours or days later, asked what happened, and then did by hand what the diagnosis called
for: cancel, run again, restart a worker, close a pull request. The **cleaner** does that noticing,
diagnosing and resolving on a schedule.

**Goals**

- Nothing reads "in progress" for long while nothing is running for it (the user's rule of 2026-11-13).
- A subject that stopped for a cause that has passed, was fixed, or has a known remedy is set going again
  without a person.
- What a round left behind (a snippets issue or pull request nobody follows, a cluster job whose round
  ended, a run no worker can execute) is closed, killed or ended.
- A problem of the installation (a worker down, a worker on old code, the cluster queue) is named as such,
  once, and is never "fixed" by acting on the subjects behind it.
- Every case leaves a record: what was seen, what was concluded, what was done, whether it helped.
- What the cleaner cannot resolve rests where a person looks (*Needs you*) with one sentence saying what is
  needed.

**Non-goals**

- Deciding what a person or a judge decides: approving or rejecting crops, approving a host, shelving,
  revoking, retiring. Subjects whose turn is a person's (`review`, `plan-review`, `staged`, `idle`) are not
  the cleaner's.
- Fixing code. A defect it finds becomes an issue in this repository; the fix is a development task.
- Disk housekeeping: only the keeper deletes under the raw and staged roots.
- Restarting services. The workers are sandboxed and cannot; the cleaner says a restart is owed.
- A one-off purge of rows and runs from before subjects existed (20 dataset rows, about 44 runs): by hand,
  once.

**Anti-goals**

- A cleaner that acts while a worker is down or on the wrong code, and cancels or re-runs everything that
  looks quiet because of it.
- A loop: the same subject run again and again at a cost nobody approved.
- A cleaner that hides a defect by re-running until it happens to pass.
- A cleaner that works against a person who is handling the subject.
- A sandboxed agent that holds the worker token or can write to the registry.

## 2. What has gone wrong so far

Collected from this installation's history (25 October to 15 November): the sessions in which a stuck subject
was reported, `notes/2026-11-10-prep-test-issue-8.md`, and the registry's timelines.

**A. Read "in progress" while nothing ran.** The stage never told; a person did.

| What happened | How long | What told, when someone looked | Done by hand |
|---|---|---|---|
| A round waited for autodev, whose agent job had failed or hit its time limit before any pull request (`empiar-10554`, `air-ug-…`) | 4 days; 6 h | snippets issue `needs-human`; no cluster job; registry unchanged | cancel, run again |
| A round waited for autodev at its revision limit (`empiar-10791`) | 1.5 h | "Needs a human" comment on the pull request | cancel, close the pull request, run again |
| A round waited at `merging` for a merge refused for conflicts (`empiar-10070`) | 7 h | pull request `CONFLICTING`; a comment | none yet |
| The snippets and autodev workers were dead (a `~` in a path) | 2 days | no poller on the queue; issues at `snippets:go` with no comment | restart |
| Every workflow task failed after the checkout changed under the workers (twice), and after a patch was removed | 94 min; a day | failed workflow task; worker log | switch back; terminate the run |
| An activity retried for hours: never registered on the worker (`read_feedback`), a write cap spent, a URL the sandbox could not reach | up to 6 h | pending activity, attempt in the hundreds, last failure | restart; config |
| The registry said `developing`, the page offered neither Start nor Cancel (`empiar-10554`) | 4 days | subject and dataset row disagreed | code fix, restart, cancel |
| A request stayed `needs-human` with every dataset prepared | hours | the datasets' rows | stage written by hand |
| A run of a workflow class no worker has any more logged an error every 8 minutes | 2 days | worker log | terminate |

**B. Stopped with a reason, and the remedy was mechanical.**

| What happened | Remedy that worked |
|---|---|
| A host stalled or cut a read (EBI: timeouts, truncated bodies, a 403 after hours of good answers) | run again later |
| A defect in the worker stopped the round (a 310 KB binding in a comment, a commit compared instead of stamped, a folder rule) and was fixed the same day | run again after the restart |
| The catalog record lacked something (no file URL, label class undecided) and was corrected | run again |
| A needed host was not approved | a person's click, then run again |
| A job hit its time limit on a slow host; the timeline said only "exit 140" | not established; a debugger's probe decides |

**C. Left behind.**

| What was left | By what |
|---|---|
| Snippet pull requests and issues nobody followed, each polled every two minutes (#41–#45, #52, #53) | rounds that ended another way |
| 155 dataset runs, 28 agent runs and 39 cluster jobs | a request cancelled while its cancel was swallowed |
| Buffers of failed rounds, still registered | rounds that never retired them |

Three facts from this list shape the design. Most of class A is one of five observable conditions, none of
which needs an agent to see. The remedies of class B are a `go` at the right moment. And several cases had a
cause nobody had seen before, which a rule written in advance would not have matched.

## 3. Approaches

1. **Rules only.** A scheduled pass matches each stuck subject against a table of known conditions and applies
   the remedy. Cheap and predictable. Every incident above that was new when it happened would have fallen
   through, and falling through is what the user asked to end.
2. **An agent only.** A scheduled agent with the registry, Temporal, the cluster and GitHub in reach decides
   everything. Covers the unforeseen. It spends an agent run on conditions a comparison settles, it cannot be
   tested against fixtures the way a table can, and an agent that can cancel and close things by its own hand
   is a sandboxed job holding the worker's authority.
3. **A sweep, a playbook, and a diagnosing agent for the rest (picked).** A deterministic sweep gathers
   evidence and names what is stuck. Known conditions are remedied by rule. Anything else, and any rule
   whose remedy did not help, goes to an agent that reads the evidence and proposes remedies from a fixed
   menu; the worker checks each against the stage table and the limits and carries it out. The agent is the
   debugging agent's sibling: that one diagnoses a failed round from inside its workflow, this one diagnoses
   what no workflow can see about itself.
4. **More timers inside the workflows.** `round-fixes` does this for the wait on autodev, and it stays: it is
   the fastest and most exact answer where a workflow can know. It cannot cover a workflow that is not
   running, a worker that is down, or what a round left behind.

## 4. Design

### 4.1 The parts

- **Sweep.** The `MiaCleaner` workflow runs on a schedule in the mia-buffers worker (every `cleaner.minutes`),
  beside the keeper. Its one activity reads the evidence (§4.2), names the service findings (§4.3) and the
  stuck subjects (§4.4), and opens or updates a **case** for each.
- **Case.** One occurrence of one thing being stuck, a row of the ledger (§4.8). A case in work is a `MiaCase`
  workflow with the case's id, so two sweeps never work one case and a case survives a restart.
- **Playbook.** The table of §4.5: condition, remedy. Code, with a fixture per row.
- **Diagnosis.** An agent job for a case no rule covers (§4.6).
- **Remedy.** One entry of the menu of §4.7, carried out by the worker.

A case goes: opened → (rule or diagnosis) → remedy → **checked at a later sweep**. If the condition is gone
the case is `resolved`. If it is still there the case goes to diagnosis once, with what was tried; after
that, or when the limits of §4.9 are reached, it is `needs-person` and says what is needed.

### 4.2 What the sweep reads

All read-only, by the worker, through clients it already has:

- **Registry:** each subject's stage, status word and last write; its timeline; its actions and their states;
  the job records of its last round; shelving; locks.
- **Temporal:** per subject, whether a run is open; its pending activities (type, attempt, last failure, last
  heartbeat); a failing workflow task; the time of its last event. Per task queue, whether a worker polls.
  Per schedule, when it last fired.
- **Cluster:** the state of every job whose record has no end.
- **GitHub, snippets repository:** for a dataset in the develop path, the issue's state and label, the pull
  request's state and whether it can merge, autodev's last comment (what `autodev_look` reads).
- **Code:** the commit each worker started on, which a worker writes to the registry when it starts, and the
  checkout's current commit.

### 4.3 Service findings come first

Before any subject is judged, the sweep looks at the installation. Each of these is one finding for the whole
installation, shown as the page's banner and at the top of the cleaner's view, and **every subject that
depends on the affected service is skipped** until it clears:

| Finding | Seen as |
|---|---|
| Temporal does not answer; a task queue has no poller | the dispatcher's health check |
| A worker runs a commit other than the checkout's: a restart is owed | the commits of §4.2 |
| Workflow tasks of a queue fail on every attempt (code and history disagree) | failing workflow tasks on more than one run |
| A schedule has not fired for three of its intervals | the schedule's last action |
| `autonomy.pause` is set | config |
| Jobs wait in the cluster queue longer than `cleaner.pend_hours` | job states |
| GitHub or the registry refuses or does not answer for several subjects at once | pending activities' last failures |

The cleaner does nothing about these. Its part is to say them within one sweep, where the two-day outage of
the snippets worker was found by a person asking why six datasets were slow.

### 4.4 What counts as stuck

- **Quiet:** the status word is `working` and for `cleaner.quiet_minutes` none of these held: a registry
  write for the subject; a job of its round pending or running; an activity in flight on one of its first
  three attempts; a workflow timer due within the hour; a party it waits for that is itself at work (a
  dataset in the develop path whose snippets issue is `snippets:working`; a request with a dataset that is
  not at rest).
- **Stopped:** the status word is `stuck` (`failed`, `blocked`, `needs-human`) for `cleaner.stopped_minutes`.
  Looked at once per stop, and again only when something it depends on changes (§4.5, *input changed*).
- **Left over:** a snippets issue or pull request, a cluster job or a run that outlived what it was for
  (the rows of §4.5 say when).

Not stuck, and never touched: `waiting` (a person's turn), `done`, `not started`, anything shelved, and any
subject a person acted on within `cleaner.hands_off_hours`.

### 4.5 The playbook

Each rule names what the sweep sees, what is done, and the incident it comes from. `go`, `cancel`, `stop` and
`recheck` are actions sent to buffer-api as the actor `cleaner`.

**State repairs** (the registry and what runs disagree)

| Rule | Sees | Does |
|---|---|---|
| no run | `working`, and Temporal has no open run for the subject | `cancel` (buffer-api ends the round itself), then `go` |
| frozen run | a failing workflow task on this run only, with the workers on the checkout's commit | `stop`, then `go`: a go starts a run on today's code. Reports a defect |
| unrunnable run | an open run of a workflow type no worker registers | terminate it |
| activity retrying | a pending activity past its 10th attempt or 30 minutes | "not registered": the restart-owed finding. A refused or unreachable service: wait. Anything else: diagnosis |
| request behind | a request at `requested` whose datasets all rest, or at `needs-human` whose datasets are all prepared or shelved | `recheck` |
| left-over job | a job pending or running 10 minutes after its round ended | kill it |

**Remedies** (the subject stopped, or waits on a party that stopped)

| Rule | Sees | Does |
|---|---|---|
| autodev's run failed | the snippets issue is `needs-human` after a failed or timed-out agent job | once per issue: comment, re-add `snippets:go`; then `go` on the dataset, which resumes the issue |
| merge conflict | the dataset stopped at `merging`; the pull request cannot merge | `/revise` asking autodev to merge `main` and change nothing else, then `go`; with no revision left: close the pull request and issue, `go` from the match |
| revision limit | autodev stopped at its revision limit with crops still failing | diagnosis |
| passing cause | the stop names a timeout, a reset or truncated read, a 5xx, a 403 or 429 from a host that answered earlier in the round, or a lost job | `go` after `cleaner.retry_hours`, at most twice, the second after six times as long |
| fixed since | the stop is the worker's own (an activity's error, not a job's result), and the worker has started on another commit since | `go`, once per commit |
| input changed | since the stop, the record's file in the catalog changed, a host the stop names was approved, or a limit the stop names was raised | `go`, once per change |
| time limit | a job ended at its time limit | diagnosis (a slow host and a volume too large need different answers) |
| host not approved | the stop names hosts not allowed | nothing; `needs-person`: approve them at Start |
| record gap | the match agent stopped `blocked` asking for a decision or a URL in the record | nothing; `needs-person`, quoting what it asked for; *input changed* takes it up when the record changes |

**Leftovers**

| Rule | Sees | Does |
|---|---|---|
| left-over snippet work | an open snippets issue or pull request of ours whose dataset is prepared through another reader, is shelved, has opened a newer issue, or has rested for `cleaner.leftover_days` | close both with a comment that says why; autodev's run ends on the close |

### 4.6 The diagnosis agent

For a case no rule matched, a rule sent on, or a remedy did not resolve. A csub agent job like the debugger's,
with the debugger's tools (read, search, `harness list` and `harness smoke` against the record's own hosts),
its budget reserved before it runs.

Its workspace holds, all prepared by the worker and read as untrusted: `case.md` (what the sweep saw, and why
no rule decided), the subject's timeline, the records of its last round's jobs, Temporal's description of its
run, the snippets issue and pull request with their comments, the service findings, what earlier cases of
this subject tried, and `playbook.md` (the menu of §4.7 with the limits).

It writes one `outcome.json`:

```
{"diagnosis": "<the cause, with the evidence for it>",
 "cause": "passing | data | record | defect | service | autodev | unknown",
 "remedies": [{"do": "go", "note": "<advice for the match agent>"}, ...],
 "needs": "<what a person has to do, when no remedy would change the outcome>"}
```

Its rules are the debugger's: never invent a cause; choose by what would be different next time; when nothing
would be, say what a person must do, since a second identical failure helps nobody. A `defect` always carries
a `report_defect`, whatever else is tried.

### 4.7 The menu, and who carries a remedy out

| Remedy | Carried out through |
|---|---|
| `go` (with a note), `cancel`, `stop`, `recheck` | buffer-api's action routes, as actor `cleaner` with the worker token: the stage table decides whether the subject takes it |
| comment, `/revise`, re-add `snippets:go`, close a pull request, close an issue | the worker's GitHub client on the snippets repository, where the worker already opens these issues |
| kill a job | the job runner (`csub kill`) |
| terminate a run | Temporal, for the *unrunnable run* rule alone |
| `report_defect` | an issue in this repository: title, diagnosis, evidence, the cases it explains; one per defect, found again by a marker |
| `wait` (hours), `needs` | the case alone |

The agent proposes; the worker carries out. The agent holds no token and reaches neither buffer-api nor
GitHub: a broker never approves the installation's own host, and what a sandboxed job writes is reduced to
this typed result before anything acts on it. A remedy outside the menu, or one the stage table refuses, is
dropped and the case says so.

Two actions are new: `stop` for a dataset (buffers and requests have it; it ends a run that cannot answer a
`cancel`) and `recheck` as an action of a request (today a signal only buffer-api sends).

### 4.8 The record

- **Ledger:** a `cases` table, written through a worker route: the subject (or the service), the rule or
  `diagnosis`, the state (`open`, `working`, `waiting`, `resolved`, `needs-person`), what was seen, each
  remedy with its result, the diagnosis job's record.
- **Timeline:** one entry on the subject for each remedy: `**Cleaner:** <what it saw>. <what it did>.`, with
  the link to the diagnosis job's record when there was one. The actions themselves are in the action log
  like anyone's, by `cleaner`.
- **Page:** a *Cleaner* view under Operations: service findings first, then cases in work, cases that need a
  person, and what was resolved in the last week. A `needs-person` case puts its sentence on the subject's
  row in *Needs you*.

### 4.9 Limits

- At most `cleaner.max_remedies` remedies that start work (`go`, re-adding `snippets:go`, `/revise`) per
  subject in seven days. After that the case is `needs-person` and lists what was tried.
- A `go` by the cleaner is charged to the root the subject's last round was charged to, like the debugger's,
  and its round gets a debugging cycle of its own, like a person's.
- Diagnosis jobs are reserved against a root of their own, `cleaner.max_usd_per_day`; when it is spent,
  cases wait.
- At most `cleaner.max_parallel` cases in work at once, and one per subject.
- A person's action on a subject closes its open case and keeps the cleaner off it for
  `cleaner.hands_off_hours`.
- `cleaner.mode`: `off`, `report` (cases are opened and say what would be done; nothing is done) or `act`.
- Never: `approve`, `reject`, `shelve`, `unshelve`, `revoke`, `retire`, a host approval, a stage or a result
  written directly, anything deleted on disk.

### 4.10 Config

```yaml
cleaner:
  mode: act              # off | report | act
  minutes: 10            # the sweep
  quiet_minutes: 30
  stopped_minutes: 30
  retry_hours: 2
  leftover_days: 3
  pend_hours: 6
  hands_off_hours: 2
  max_remedies: 3
  max_parallel: 3
  max_usd_per_day: 20
```

## 5. What changes and what does not

**Changes**

- mia-buffers: the `MiaCleaner` and `MiaCase` workflows, their activities, a schedule beside the keeper's,
  a snippets-repository client for the worker.
- buffer-api: the `cases` table and its routes; the actor `cleaner`; `stop` in the datasets' stage table;
  `recheck` in the requests'; the worker-commit rows.
- Every worker writes the commit it started on to the registry.
- The page: the Cleaner view, the banner's findings, the line in *Needs you*.
- Two things a stage or an entry should have said, found while collecting §2: a round that waits for
  autodev's revision reads `developing`, not `testing`; a job ended at its time limit says so instead of
  "exit 140".

**Does not change**

- The stage tables remain the state machine: the cleaner asks through the action routes and is refused like
  anyone.
- Only a person's click approves a host; only the keeper deletes; shelving is a person's.
- The debugger stays inside the dataset's workflow, with its one cycle. The cleaner comes after it, and its
  `go` is a new round that may be debugged once.
- The timed wait on autodev stays the first answer where a round can know.

## 6. Build order

Each step is useful alone and gets its own plan under `docs/plans/`.

1. **See.** The sweep, service findings, cases in `report` mode, the Cleaner view. Nothing is acted on.
   After this step the page shows every quiet, stopped and left-over thing with its evidence, and says when
   a restart is owed.
2. **Repair.** The actor, `stop` and `recheck`, the state repairs and the left-over job.
3. **Resolve.** The remedies and the left-over snippet work.
4. **Diagnose.** The agent, its outcome, `report_defect`. Its fixtures are the incidents of §2: one evidence
   directory each, with the remedy that was right.

## 7. Left to the builder

- How the sweep reads Temporal cheaply for a few hundred subjects (a visibility query for open runs, a
  describe only for subjects that look quiet).
- The signature that makes two sightings one case (the rule and the round or object it is about).
- The text classes of *passing cause* and of the worker's own errors, as patterns with a fixture each.
- Where the worker's commit comes from in a sandbox with a read-only checkout.
- Whether `MiaCase` is a workflow per case or a child of the sweep.

## 8. Decisions for the user (defaults in bold)

1. **First deployment:** **rules and the agent's remedies act at once, within the limits**; or `report` for
   some days first, as the judges ran in shadow.
2. **The agent's reach:** **it proposes from the menu and the worker carries out**; you asked for a cleaner
   with access to buffer-api, and in this design the cleaner's worker has it and the agent does not.
3. **Run again after a fix (*fixed since*):** **yes, once per subject and commit**; this is what was done by
   hand after each of this week's fixes, and it re-runs every subject the defect stopped.
4. **Closing left-over snippet work:** **at once when the dataset is prepared through another reader or
   shelved; after three days when it merely rests**.
5. **Defects:** **an issue in this repository without `autodev:go`**; or let autodev start on it.
6. **Service findings:** **the page's banner and the Cleaner view**; or also a message somewhere you read
   without opening the page.
7. **Scope of the first build:** **datasets and requests in full, buffers by the state repairs alone**, since
   every incident of §2 after October was a dataset's or a request's.
