    Training on a MIA buffer

    A buffer is a pool of training crops drawn from the catalogued datasets that match a spec. The spec is a short YAML file, and it defines both ends of the buffer. On the input side it says which datasets qualify. On the output side it says how crops are presented to the model: the patch size and pyramid levels, the channels, the normalisation, the weighting between datasets, and how volumes are split into train, validation and test. The system plans the pool, downloads and converts the datasets it already knows how to read, and serves crop descriptors over HTTP; a Python dataset class turns them into tensors in the training process.

    Everything a person does is a button on this page: plan a buffer, run it, approve it, cancel it. Every step the system takes is an entry in the spec's timeline, which its page shows as it happens. Needs you lists whatever is waiting for a person. The page needs no login: anyone who can reach it can press its buttons.

    The whole loop

    Step 1. The spec

    New buffer, on the Buffers tab, builds a spec from its filters: dimensionality, licence, annotation source, whether annotations are required, the smallest array accepted, the patch size and pyramid levels, and the weighting between datasets. Each change is planned against the catalog on the server, so the counts shown are the plan that spec produces.

    • Where datasets leave counts the datasets each rule removes. The last rule, not prepared, means a dataset fits the spec but no reader exists for its files yet; the other rules are the spec's own filters.
    • Fitting datasets by modality and Weight share show the composition of the pool and of the draws. The weighting temperature runs from uniform over modalities (0) to proportional to each dataset's capacity (1).
    • Prepare these datasets files one request that hands every dataset that fits the spec and is not prepared to the preparation pipeline. (To prepare datasets of your own choosing, tick them on the Datasets tab.) Each one is an agent run that writes and verifies a reader for that dataset's files; some stop with a question for a person. The request's page lists its datasets with where each stands; every request is on the Preparation tab. A buffer plans over prepared datasets only, so a buffer started today uses what is prepared today, and a later round picks up the rest.
    • Download spec YAML saves the spec as a file, for editing by hand or for keeping with an experiment.

    The fields of a spec that are usually edited:

    name: my-2d-nuclei                      # names the spec and its page; saving the same name edits that spec
catalog: {repo: …, ref: <commit>}       # pinned by the page: the plan is reproducible
select:
  where:
    dims: {in: [2D]}
    modality: {in: [fluorescence, brightfield]}
    license: {in: [CC0-1.0, CC-BY-4.0], allow_unknown: false}
    annotations: {required: true}
sampling:
  patch: {2D: {y: 256, x: 256}, c: 1}   # crop edges in pixels at level 1; one channel per crop
  levels: [1, 2, 4]                     # the pyramid levels each crop is served at
  weighting: {scheme: temperature, over: [modality, dataset], temperature: 0.5}
  normalize: {method: percentile, range: [1, 99], scope: volume}
splits:
  fractions: {train: 0.8, val: 0.1, test: 0.1}
ready:
  min_fraction: 0.5                     # how much of each weighting group must be servable before the board says "ready"

    Step 2. Plan, then run

    Create buffer, below the filters, shows the spec as YAML, with the catalog commit pinned; edit it there if the controls do not offer what you need. Plan saves the spec under its name and starts a round that stops at its plan, before any job runs.

    The page then opens the spec's own page: its lifecycle with the current stage marked, what it is waiting for, the buttons its stage accepts, and its timeline. The plan is a timeline entry that lists the pool, one row per dataset, with weights. Run starts the jobs. To change the spec instead, edit the YAML under Edit and plan again and press Plan: a new round plans the edited text.

    Step 3. Read the board, then approve

    Sourcing runs until no dataset has a job left. The spec then moves to staged and its timeline gets the board: each dataset's outcome (with the error of one that failed), each weighting group's servable share against ready.min_fraction, volumes per split, bytes on disk, and which datasets are still waiting on something.

    Approve. Approve serves the buffer as the board shows it. A dataset that failed stays out; one that is waiting keeps its place and joins when it lands, with a new board entry. The share each group has at the approve becomes the floor it is judged against afterwards, so a partial buffer accepted on purpose is not later reported as degraded. No job runs between the approve and ready.

    Or edit and plan again. Editing the YAML on the spec's page and pressing Plan retires the staged buffer and plans a new round from the edited spec. Converted pyramids stay in the shared cache, so a second round over the same datasets skips the conversion.

    • Waiting on a drop. Some datasets sit on hosts no job may reach. The timeline lists the files to place by hand in the dataset's incoming/ directory. Once the copy has finished, press Files are in place, and the worker takes them into the cache. The button is refused while the directory is empty or a file in it changed in the last minute.
    • Waiting for a quota or a lock. The cache is full, or another buffer is converting the same dataset. Both clear on their own.
    • Day limit. A group with nothing servable after sourcing.dataset_timeout_days (default 14) drops its waiters; with nothing servable at all the spec stops at needs-human.
    • Automatic approve. plan: {auto_approve: true} in the spec approves the staged buffer without a person when every group meets min_fraction. A short group still waits for one.

    Step 4. Train

    The ready entry names the buffer id and gives this cell. It runs in the harness environment of the mia-snippets checkout, with this repository on the Python path and torch and muvit installed:

    from mia_buffers.client import BufferDataset

URL, TENSORIZERS = "<service url>", "<mia-snippets checkout>"   # or export MIA_BUFFERS_TENSORIZERS
train_ds = BufferDataset(URL, "<buffer id>", "train", n_samples=4000, tensorizers=TENSORIZERS)
val_ds = BufferDataset(URL, "<buffer id>", "val", tensorizers=TENSORIZERS)

loader = DataLoader(train_ds, batch_size=32, num_workers=8, collate_fn=BufferDataset.collate)
model = MuViTMAE2d(in_channels=train_ds.n_channels, levels=train_ds.levels, ...)
    • Train is a stream. Each item is a crop drawn by the service under the spec's weighting; n_samples is the length of one virtual epoch and the index is ignored. Val and test replay a frozen list that is the same every epoch and every run.
    • The service serves descriptors, not pixels. A descriptor names the pyramid, the window, the channels and the normalisation bounds. The training process reads the OME-Zarr pyramid from shared storage and tensorises it, so the load of a DataLoader with many workers falls on the training node. Each worker registers itself as a consumer, listed on the buffer's page.
    • What a sample holds. The image at each level in sampling.levels, the label layers the dataset has, and meta with the record, the voxel size and the crop's position in physical units. A buffer mixes datasets whose label layers differ, which is why the custom collate is needed: a batch keeps the keys every sample has.
    • What is pinned. The buffer records the catalog commit, the spec hash, the plan hash and the commit of the conversion code. A checkout at a different commit raises on construction; allow_recipe_mismatch=True turns that into a warning.
    • Before the approve, while the buffer needs a human, or when it has no approved event, the service answers 409 with the reason and the client raises BufferNotApproved. After a retire it answers 410. A split with nothing servable yet raises BufferEmpty.

    Step 5. During training, and afterwards

    The Buffers tab lists every spec and every buffer with its latest event; a buffer's own page has the board, the volumes per split, the consumers seen, the draws per day and a health line. After ready the spec changes only when one of these happens:

    • Degraded. When a group's servable share falls under the floor set at the approve (a pyramid was evicted or lost), the timeline says so and the worker stages the missing datasets again from the cache.
    • Idle. No consumer for idle.hours (default 72) moves the spec to idle; Keep returns it to ready. After retire_after_days (default 14) more days without a draw the keeper retires the buffer and its space is reclaimed.
    • Revoked. Revoke the ticked removes single datasets from the serving buffer; Retire releases all of it.
    • A new round. Plan with the same or an edited spec builds a buffer with a new id, reusing what is in the cache. The Buffers tab marks the earlier buffer superseded.

    prepareda dataset with an approved reader and verified sample crops, produced by the preparation pipeline. Only prepared datasets enter a plan.
    spec, buffer, rounda spec is the YAML you save and run; a buffer is one served pool of crops built from it. A spec runs one round at a time; each round builds a buffer with a new id.
    stage, timelinea spec, a dataset and a preparation request are each in one stage at a time, and the stage decides which buttons are offered. The timeline is the list of everything that happened to it, newest first.
    weighting groupthe datasets that share the first key of weighting.over, a modality for instance. min_fraction and the floors are per group.
    stagedconverted: a dataset's volumes rewritten once as immutable OME-Zarr pyramids in the shared cache, reused by every buffer that needs the same geometry and plan.
    crop, levela crop is one training window, served at each pyramid level the spec lists, all centred on the same point: level 1 is full resolution, level 2 half, and so on.

    How the services, workflows and storage fit together is in Architecture.

    architecture · mia-data, mia-buffers and buffer-api

    MIA Training Buffers

    The system is two pipelines that share one registry. mia-data turns a catalog record into a prepared dataset, which means an approved binding and verified crops on shared storage. mia-buffers turns a buffer spec into served crops. It plans over prepared datasets only, fetches the raw files once into a shared cache, stages each volume as an immutable OME-Zarr pyramid, and registers each pyramid with buffer-api, the one service that picks every crop. Training jobs pull crop descriptors from the service and read the pyramids themselves.

    buffer-api also serves this page, which is how a person starts, approves or cancels anything. A button is a request to buffer-api; the service checks it against the stage of the thing it is about and passes it to that thing's workflow. Every step a workflow takes is written to the registry as a stage and a timeline entry, and the page follows them as they happen.

    1. System layout

    One host runs everything that holds a credential: Temporal, the two workers and buffer-api. Jobs run on the cluster and see only files. In the figure, lines run in the gutters between columns, and each later figure drills into one part of this one.

    In the figure, data preparation runs along the top and buffering along the bottom.     3. How a dataset becomes prepared

    A dataset is prepared when its latest round ended done with a binding and a manifest saved. Its state is the word for a person: in-progress while a round works by itself, needs-human whenever a person has to act (crops to review, a stopped or cancelled round), prepared after that. Running a prepared dataset again takes it out of prepared until the new round's crops are approved. A buffer plans over prepared datasets only, and asking for more datasets to be prepared is its own, explicit request. Preparation judges nothing about who may use a dataset. Licence, modality, organism, annotations and fit at a given patch size and set of levels are all filters of a buffer spec, and the planner evaluates them per spec. A dataset of 60-pixel images is therefore prepared like any other and simply fails the fit rule of a 256-pixel buffer. The only place preparation stops is a needs-human stage.

    3b. The review loop

    Every set of crops waits at review, including a set made from a snippet PR. Approve on the dataset's page saves the set the reviewer looked at. When that set came from a PR head, the worker first has autodev merge that head, and the same files are saved under the merge commit. Reject sends the feedback typed with it to the agent. When the round is following a PR, the feedback goes as /revise on that PR. Otherwise it goes as a new mia-snippets issue asking for a snippet that supersedes the one at fault, because a merged snippet is never edited. The next set of crops comes back to review, and the loop continues until the reviewer approves.

    Every verdict is written to the registry as an assessment before anything acts on it. A judge, a second model that reads the same gallery, can look at each set first: in shadow mode its verdict is recorded beside the person's and decides nothing, and the Decisions tab shows how often the two agree. Revoke at any later time withdraws a saved set: its artifacts are quarantined, the buffers that drew from it unregister the dataset, and Run again on the dataset's page repairs it.

    4. From a click to a stage

    A dataset, a buffer spec and a preparation request are each a subject in the registry: a key, a stage, a revision that rises with every stage, and a timeline. One table per kind (STAGE_ACTIONS in mia_data/config.py and mia_buffers/config.py) says which actions each stage accepts and whether a round is in progress there. buffer-api refuses anything the table does not list, and the page offers only what it lists. The workflow is the only writer of stages, and every stage write is awaited, so the registry's stage is the workflow's.

    subjectits pageaction routeactions
    dataset#datasets/<record>POST /datasets/<record>/actionsgo (Start, Run again, Restart at review), approve, reject with a note, revoke, cancel
    buffer spec#specs/<name>POST /specs · POST /specs/<name>/actionsgo with plan_first (Plan), approve (Run at the plan, Approve at the board), keep, retire, revoke, dropped (Files are in place), cancel, stop
    preparation request#requests/<key>POST /prep · POST /prep/<number>/actionsgo, cancel, stop

    Cancel and force stop. cancel ends a round in progress: the round starts no new activity, every cluster job it waits on is killed by id, locks are released and the stage becomes cancelled. A job that cannot be killed ends the round in needs-human naming it. stop terminates a workflow that does not answer a cancel and retires the spec's buffers; it does not kill a job already running. The pause. mia pause sets autonomy.pause in mia.yaml; every workflow stops at its next job with a needs-human entry that starts "paused by the operator", until mia resume.

    5. Lifecycle of a buffer spec

    A buffer spec is in one stage at a time. A person moves it with Plan, Run, Approve, Keep, Retire and Cancel the round; the worker and the keeper make every other transition. A round stops twice for a person: at its plan, before any job runs, and at staged, before anything is served.

    6. Sourcing one dataset

    Once a round is running, the worker sources every dataset in the pool, heaviest first, so the datasets that supply the most crops are staged earliest. Each dataset passes through the two phases shown in figure 6, a fetch and a stage. A record's raw cache is written by one job at a time, across both pipelines and any number of buffers. A lock file on the host's local disk enforces that.

    7. The cache and its keeper

    The cache is two shared roots, the raw root and the staged root, and both are reference-counted through the registry. Nothing in the service deletes. Only the keeper, which runs inside the buffers worker, removes a directory.

    8. Serving

    Train consumers get a stream of crops, and val and test consumers get a frozen list. Both kinds read the pixels from shared storage themselves.

    9. What a crop is

    The service hands out descriptors, not pixels. Whoever tensorises a crop derives one pixel box per level from the descriptor and reads it from the pyramid. The example in figure 9 uses the U937 confocal record, with 45 nm pixels, 256-pixel patches and levels 1, 2 and 4.

    10. Where things live

    One configuration file serves every service on the host. Anything that needs a working lock lives on host-local disk, and everything a job or a consumer reads lives on shared storage.

    What is not built

    • Identity: the action routes take no login, so the registry records an action but not who pressed the button. A proxy or token layer in front of buffer-api would name the actor.
    • An active judge: a judge runs in shadow only; its verdict is recorded and decides nothing.
    • Remote mode: crop workers beside the service that tensorise and return tensors over HTTP. Local mode, where the training job reads the pyramid, is the only mode.
    • Several worker hosts: the lock directory assumes one host. The upgrade is a lease table in the registry with the same four calls.
