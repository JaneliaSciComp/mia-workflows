Developer guide

MIA Buffers: architecture and operations

Training a foundation vision model for microscopy requires diverse examples from datasets distributed across the internet. The challenge is to draw enough examples from enough different sources without storing all of them in full. The architecture separates learning how to read a source from reading the samples an experiment needs. The user guide explains how to create a buffer and use it in training.

1. Why this architecture exists

The upstream pipeline handles source diversity. Starting from a catalog record, an AI agent looks for a snippet, a small program that reads the dataset’s files. If none fits, an AI coding agent can write one. Jobs test the reader against the source and produce crops for review. The result is a checked way to read that dataset, not a local mirror of its images.

To limit storage use, the downstream pipeline builds a buffer: a pool of image samples for training. It plans samples across prepared datasets and stages the image chunks those samples need. A reader fetches a whole file when it cannot read just the relevant ranges. Training then reads from shared storage. On demand here means staging for a requested buffer, not contacting the source for every training batch.

Three kinds of state

A workflow is a sequence of decisions that can pause and later continue. Temporal records the decisions and completed activity results. The registry is the view that people and other workflows can query: which datasets are prepared, which buffer versions are serving, and why work stopped. Storage holds the evidence and the pixels. These are deliberately separate. A row saying “prepared” is not an image, and a directory of files is not an approval.

Components at a glance

  • buffer-api provides the page, registry, ledger, action routes and sample service. Its ledger is a SQLite database, a file on a disk attached to the service host.
  • Temporal records workflow histories and coordinates durable waits, timers and retries. Workers execute workflow code and activities.
  • mia-data prepares datasets, checks bindings and crops, and records the results. It can request reader development from autodev.
  • autodev works on GitHub issues and pull requests using a sandboxed coding agent. It is the exception to the rule that dataset and buffer issues are not inputs.
  • mia-buffers plans buffers, coordinates staging and preparation requests, and runs the cache keeper and repair agent.
  • mia-snippets is a separate checkout containing readers and the harness, the shared software that plans, stages and checks samples and converts them into tensors for the model.
  • csub and LSF run jobs under policy on the cluster. Shared storage holds prepared outputs and caches.

The page and workflows use buffer-api as their shared record of subject stages and timelines. Dataset and buffer GitHub issues are mirrors of that record, not a source of actions. The snippets repository and autodev retain their GitHub-based review loop.

Trace a decision from the browser to the ledger

Suppose two reviewers have the same gallery open. An approval must not silently apply to the next crop set that appears. The page sends the crop set ID, the dataset revision displayed and an action key. The API checks the revision and the actions allowed at the current stage. An obsolete decision is refused. Retrying a delivery with the same key does not ask the workflow to act twice.

MiaMirror copies timeline entries to the corresponding GitHub issue. That copy is for readers. Editing it does not change the ledger, approve a gallery or start a buffer.

2. Follow a dataset

From catalog entry to prepared data

A dataset round is one run of dataset preparation. It records the exact versions of the catalog, readers and harness it will use. The dataset round establishes a binding that specifies how a reader opens this dataset’s files. It then checks the binding, makes and verifies example crops, and obtains a verdict. When a reader needs development, autodev works on a snippets issue and pull request. The dataset workflow periodically checks that work and has a timeout rather than waiting forever.

The crop judge can be off, shadow or active. Shadow assessments do not decide. An active judge may approve or request rework within the configured limit. Uncertain cases and unresolved findings go to a person. A human verdict overrides judge and developer assessments of the same crop set. The saved binding, crops and registry row make the dataset available to buffer plans.

The initial check opens the bound arrays and reads a patch. If a reader is missing, the dataset workflow opens a snippets issue. Autodev runs its coding job on a branch and proposes a pull request. A new snippet name ends in the issue number so independently written readers do not collide. Failed verification goes back with a report. A commit-free response does not certify good crops. Only a validated no-change response to the specific request counts as an answer to crop findings.

During an external wait, autodev_look checks the snippets issue every 15 minutes. A pull request update can wake the workflow earlier. A stopped agent or a quiet period beyond limits.autodev_quiet_hours ends the wait with an explanation. The workflow does not leave a dataset waiting indefinitely for a commit.

Dataset rounds and preparation requests

A preparation request coordinates multiple dataset rounds through buffer-api. A buffer does not start dataset preparation itself. Resume keeps the dataset round’s pinned inputs and completed results and starts at the first unfinished step. Restart discards dataset round state and pins current inputs. A force stop loses the workflow's stored results. Each repeated step receives a new attempt identity so that jobs and timeline markers remain distinct.

The API calls each dataset, preparation request or buffer a subject. Its stage determines which actions are valid. A human can shelve a resting subject, and the API keeps the hold separately from its stage. A shelved dataset is excluded from buffer plans and preparation requests. Preparation requests recheck their datasets when relevant changes occur.

3. Follow a buffer

The buffer plan comes before staging

The buffer definition selects catalog records and specifies sampling, splits and presentation. Planning uses prepared records, calculates weights and crop targets, and pins the inputs needed to reproduce the buffer plan. A buffer round started from the page stops for buffer plan review before staging.

The contract between the two workers

MiaDataDataset saves the reviewed crop set, its binding.yaml and a manifest.json naming the saved binding. It publishes a prepared row to the registry. A hand-placed binding by itself is not a prepared dataset. The row answers “is there a checked way to read this record?” It does not answer “is it suitable for this model?” That depends on the buffer's licence, geometry, weighting and split rules.

MiaPrep asks for dataset actions through the API and follows the registry. It identifies the originating request so the jobs it starts count against that request’s budget. MiaBuffer does not make those requests. The buffer round reads the prepared dataset rows at planning time. The separation lets one preparation support several buffers without allowing a change to one buffer definition to launch a fleet of reader-development jobs.

The buffer round saves spec.yaml, pins.json and the resulting buffer plan. Its dataset rows describe the source records, weights, split rules and sampling recipe. The buffer planner does not read image pixels or enumerate every final window. The harness derives the sample locations and the stage job determines which candidates meet content filters.

Where a buffer round can wait

Buffer stageMeaning for the next operation
newThe buffer definition exists. No cluster work follows merely from saving it.

Quota and lock waits use a shared timer with backoff rather than one busy loop per record. Before approval, sourcing.dataset_timeout_days bounds waits for groups with nothing available. When nothing can serve, there is no partial pool to approve.

Stage only what samples need

Each stage job reads the source as needed by planned samples and writes one sparse OME-Zarr 0.6 pyramid per volume. OME-Zarr stores an image as arrays of small blocks called chunks. Sparse means the pyramid describes the volume at each resolution but only stores chunks touched by the samples. The harness checks the pyramid before the worker saves it by rename. Source files that must be fetched whole enter the raw cache. Range reads are made on demand. A per-job transfer cap still applies, and the raw quota controls when staging waits for space.

Content and label filters run in the stage job on candidate full-resolution boxes. The planned count is an upper bound when filtering is enabled. The staging result records the actual selection, and registration adjusts the weight of a short volume. No planner estimate redistributes its missing share.

Stages share the record lock with preparation. The worker checks for an existing artifact, waits if the cache exceeds its quota and limits parallel jobs per source. A file supplied through incoming/ follows a different path: the worker checks the drop and the job reads cached files without network access. An online rebuild can read the source again. A manual rebuild needs the files still in cache.

harness stage writes to a temporary build directory. harness check-stage verifies the result before the worker renames it into place. The pyramid records its derivation under attributes.mia. A failed build is not a published artifact. With filters enabled, 2,000 consecutive rejected draws stop the search. Labels are checked before image content to avoid unnecessary raw reads. A labelled filter leaves a dataset out of the plan when its binding reads no label array. Whether a labelled dataset has annotation where its crops fall is known only to the stage job.

Register and serve

The API registers staged volumes and serves descriptors for planned samples. Training draws are weighted and sampled with replacement. Validation and test use frozen lists. A client reads the pyramid from shared storage and tensorizes the crop locally. The ledger records draws and consumers. The Source step shows the fraction of datasets in each group whose samples are available to serve. Dropped datasets are excluded. The floor after approval is the lower of the required fraction and the fraction accepted in that group. A deliberately accepted shortfall is not itself degradation.

An artifact ID hashes its recipe, including the binding, levels, voxel size, harness commit, environment and the digest of the dataset’s sampling rule. Matching recipes can reuse staged data. A new artifact for a volume changes its frozen evaluation lists. Staged artifacts are immutable after the worker's rename.

Under /buffers/{id}, a process registers at consumers for its split. Training requests next. Validation and test request a page from split/{name}. A descriptor names a path, plane, centre, levels, channels and normalization information. The client combines those with the pinned tensorizer recipe. Workers in different processes register separate consumers.

The service refuses an unapproved buffer version (HTTP 409), returns no sample for an empty split (204), and refuses consumers after retirement (410). Frozen evaluation lists apply to the registered artifacts. Replacing an artifact can invalidate a list. For comparisons across runs, retain the buffer version ID and inspect its events for a rebuild or withdrawal.

4. Storage and safety boundaries

Storage has distinct purposes

  • Host-local state holds the ledger, locks and managed Temporal state. It must not be placed on a network filesystem.
  • Prepared outputs hold bindings and reviewed crops that establish whether a dataset is ready.
  • Raw cache holds source files fetched whole or placed by hand. A record-specific lease allows only one job to write a record's cache at a time.
  • Staged cache holds immutable sparse pyramids shared by buffer versions.
  • Job records hold requests, outcomes, log tails and, for agents, sanitized conversation and prompt information.

The cache keeper is the only component that deletes from the raw and staged caches. It takes the record lock before removing data. A lost raw-cache lease causes the waiting worker to kill the job and fail the round. A stale lease alone does not prove that its former writer stopped.

Revocation is different from eviction. A revoked artifact is quarantined for autonomy.quarantine_days rather than immediately reused or removed. The keeper also reports missing pyramids. A ready workflow rechecks the report and can rebuild under the original recipe. An unresolved loss below the accepted group floor can leave the buffer waiting for human action.

Useful paths, relative to the installation

Access is intentional

The page stores no worker token. Page actions are checked against stage rules and request work from workflows. Worker routes that write results require the service token and use the shared registry client. Consumers receive sample descriptors, not permission to write workflow results. Restrict access to the page itself because it has no built-in login.

Sandboxed job output is untrusted. Workers read it through size and symlink checks, reduce it to typed results and neutralize text before posting it to GitHub. Job sandboxes cannot write the job-record directory. Network access follows the csub broker policy. Only a person's start action approves additional hosts, and approval updates the generated broker policy. A job still requests only hosts allowed for its work. A refused host is recorded, not automatically approved. Access to raw.githubusercontent.com requires separate approval for each dataset.

5. Operate an installation

Configuration and prerequisites

mia.yaml is the deployment configuration. mia.yaml.example documents the settings. Service-specific blocks overlay shared settings, and MIA_CONFIG can select a different file. An installation needs the configured Temporal service, worker environments, a snippets checkout, cluster access, shared storage, a broker policy and the appropriate GitHub credentials.

Place paths.local_root and managed temporal.state_dir on host-local disk. Protect the service token file, which authorizes worker writes. Keep the broker policy directory separate from paths mounted read-write into worker sandboxes. The operator's base policy remains distinct from the generated broker policy and approved-host list.

limits controls individual jobs. quota controls cache management. autonomy sets request-wide budgets and the pause switch. For example, limits.job_bytes bounds a single job’s transfer, while autonomy.root.max_fetch_bytes bounds the work charged to a request across jobs. The raw quota is a threshold for eviction and waiting, not a maximum upstream dataset size. A concurrency limit makes a job wait. Reaching a spending cap can stop the round.

Start, stop and observe

Use pixi run mia up to start the configured stack and pixi run mia down to stop it. Workers stop gracefully and hand activities back to Temporal. Among application services, the API starts before the workers and stops after they drain. Managed Temporal starts before the applications. pixi run mia restart restarts application services without restarting Temporal unless it is named. Consult pixi run mia --help and the repository deployment guide for service selection, deployment and recovery details.

The page reports health and installation findings. A round may report “paused by the operator” when autonomy is paused. The repair agent checks service problems before acting on subjects and uses the same revision-checked action routes as a person. It leaves subjects behind service failures alone. Review the timeline, linked job record and service health before intervening. Cancel a round before considering force stop. Force stop does not kill a job already running.

The API makes scheduled SQLite backups under state_dir/backups. If the live ledger is missing and backups exist, startup refuses to create an empty ledger and identifies the newest backup. The operator verifies the intended installation and restores the chosen backup to the configured ledger path before starting the API. This restores registry data, not Temporal history or image files. The recovery plan must cover those separately.

Commission and verify a deployment

  1. The operator installs the locked Pixi environment and provides the sandbox and mia-snippets checkouts. The harness checkout must be visible to cluster jobs. Staged paths must resolve on training nodes as well as on the worker.
  2. The operator configures service blocks, work and storage roots, repositories, and the csub base policy. If the service host cannot submit to LSF directly, the relay connects to a submit host over SSH. Production and development require separate state, policies and credentials.
  3. pixi run mia init-token creates the worker secret named by service.token_file. The API URL must be reachable from the worker sandbox. A loopback address inside that sandbox does not reach the host service.
  4. For each configured service, pixi run mia exec SERVICE check checks its configuration. After startup, pixi run mia ps shows processes. Overview reports whether workers actually poll their queues. A process listing alone cannot confirm that a workflow can advance.

How repair decisions are bounded

A stage describes where a round is. A phase says whether it is working, waiting, stopped, done or not started. The API combines that phase with shelving and the repair case to compute the status on Overview. A repair case is a record of attempted remedies, not a second list of tasks for people.

The repair agent first looks for installation-wide problems such as an unavailable worker. For a subject it can act on, it reads the revision, chooses from a fixed set of remedies and submits a keyed action. It cannot write a success stage or declare a dataset prepared. It will not start another round over a live job left by the old one or override a person who intervened after the case opened. A repair requiring new pins must restart the dataset rather than resume it.

Release and recovery

In a release installation, pixi run mia release TAG installs a tagged checkout with its lockfile, verifies the configured services, switches the current link and restarts the applications. A previous installed tag can be selected the same way. Switching code does not rewind the ledger or Temporal histories. Deploy the harness first when a worker change depends on it. A round pins the harness at its start.

For a controlled pause, pixi run mia pause prevents new jobs at their next submission check. It does not interrupt a job already running. pixi run mia resume lifts that installation switch. Resuming an individual stopped dataset is a separate page action. A repair case must not restart work while a job left by the old round is still alive.

6. Develop safely

Find the code

mia_core holds shared configuration, locks, registry and job-record helpers. autodev provides the GitHub and job machinery. mia_data owns dataset preparation. mia_buffers owns buffer workflows, the API, client and page. mia_ops manages services. The import direction is deliberate. Buffers can import data and autodev. Data can import autodev. All three can import core. Core must not import any of the applications.

Workflow modules make deterministic decisions. An activity is the retryable unit that talks to a filesystem, API or cluster. A workflow decides which activity comes next from its recorded inputs and results, not from a live network call. Activity result dataclasses are part of recorded Temporal history. Add fields with defaults and do not rename or remove existing fields. Changes to workflow commands require replay compatibility, normally through workflow.patched() and a recorded replay fixture.

Change behavior at its source

Stage and action tables define what each subject accepts and whether a round is open. Add a stage or action there first. Stage transitions are awaited and each active stage pass records its start and result. A workflow writes its results to the registry, not to its mirrored GitHub issue. The API computes human-facing status from the stage, hold and repair case.

Job submission and waiting must tolerate retries and worker restarts. A job is started at most once per key and found again by ID. Activities with a heartbeat timeout must use the heartbeat decorator. Only the job runner writes job records. New data transfers must be bounded by what planned crops touch.

Trace two representative changes

A new dataset step. Its stage and permitted actions belong in mia_data/config.py. Its result belongs on DatasetState, with a corresponding rule in resume_step. Build the activity key, workspace and timeline marker from the round and attempt. Record the outcome before leaving the stage. Test both a first pass and a resume after that step failed, as well as replay of an older history.

A new crop filter. The buffer definition grammar is in mia_buffers/spec.py. The predicate belongs in the snippets harness, where the pixels are available. The planner includes configured filters in the recipe but must not insert an empty filters key. That would change the digest of every dataset’s sampling rule and restage every unaffected buffer. Test a full selection, a short selection and an unchanged recipe with filtering absent.

Review a change to the service boundary

The page may read results or request an action. It may not declare that a job succeeded. Put worker result writes behind the token and call them through mia_core.registry.Registry. Validate an action against the stage table, the revision and, for a crop verdict, the crop set ID. Preserve the one-way mirror. A comment on the copied issue cannot be an alternative control for the same workflow.

Workflows can wait through a deployment. In a workflow test, replay a recorded history as well as testing a fresh start. If an intentional change issues different Temporal commands, the older path must still replay. A successful fresh run alone cannot establish this. In an activity test, simulate the worker stopping after submission but before recording completion. The retry should attach to the existing job rather than submit another one.

Check changes

Install the environment with pixi install. Before pushing, run the following from the repository root. Tests include Temporal replay and do not require a live GitHub service, cluster or Temporal server. 

pixi run fmt
pixi run lint
pixi run typecheck
pixi run test

The page is static HTML, CSS and ES modules with no build step. Modules must not form import cycles or touch the DOM at import time beyond the established DOM module. Insert job and record output as text, never as HTML. For work on an installed release, consult the files at that release tag. The main branch also provides the repository rules, developer reference with replay commands, autodev runbook and deployment and release procedures. Dated specifications and implementation plans are historical design records, not necessarily current behavior.
