User guide

From datasets to training samples

Training a foundation vision model for microscopy takes more than a large number of images. The model needs examples from many kinds of specimens, microscopes and imaging methods. That diversity exists across datasets on the internet, but downloading every collection in full would take too much storage.

Instead of copying entire collections, the training pipeline samples image regions called crops. When an experiment needs them, the pipeline stages a pool of crops on shared storage. This pool is the buffer that the training job reads from.

Sampling at this scale depends on knowing how to read each source correctly. In the preparation pipeline, AI agents look for an existing piece of code that can read the dataset. If none fits, an AI coding agent writes a new reader. These small readers are called snippets. The pipeline tests the reader and produces example crops for review. Once a dataset is prepared, different experiments can sample from it without repeating that work.

This guide explains how AI scientists can select datasets, review samples and train a model with a buffer. The companion Developer guide explains how the system is built and run.

1. How a buffer works

From available data to the samples a model needs

Building a buffer brings together two choices: which datasets can supply reliable images, and which samples the experiment needs from them. Dataset preparation addresses the first question. It starts with a catalog record, which describes a dataset and points to its source files. A dataset is prepared once its reader has been checked and its example crops approved. Those crops show how the reader interprets the images. They are not the samples selected for training.

The buffer definition answers the second question. It describes which datasets suit the experiment, how much of an image each crop should cover and how often different sources should contribute. Applying those rules to the prepared datasets produces a buffer plan. It lists the matching datasets and how many crops to stage from each.

The buffer plan contains no pixels. During staging, the pipeline reads from the sources and writes the image data needed for those crops to shared storage. The buffer built from one buffer plan has its own buffer version ID. Once that buffer version is approved for training, a training job uses the ID to request samples and reads their pixels from shared storage.

The six steps on the buffer page

Where people make decisions

The AI scientist decides what the model needs to learn. The pipeline can apply sampling rules, but it cannot decide which imaging methods matter for the experiment. The AI scientist makes that choice in the buffer definition and reviews the mix proposed in the buffer plan. The same judgment matters after staging: even if most of the planned crops are available, a missing imaging method may be reason to wait before training.

The needs human status distinguishes work that calls for a person from work the pipeline can continue on its own. It does not necessarily mean something went wrong. A buffer plan may simply be ready for a decision. During dataset preparation, a reviewer may instead need to inspect example crops to decide whether the reader interpreted the images correctly. The Needs human section of Overview brings these decisions and any problems that need attention into one place.

2. Find and prepare datasets

Why preparation comes first

A catalog entry describes a dataset, but it does not by itself guarantee that its files can be read correctly. Preparation establishes a reader and binding, checks example crops, and saves the result for future buffers. A reader is a small program that interprets image files. A binding connects that reader to the files and arrays of one particular dataset. A preparation request groups datasets that need this work.

Start preparation

On the Datasets tab, the user selects records and requests preparation. The Prepare step of a buffer offers the same choice for matching datasets. The request tracks each dataset separately. On a request, Resume leaves prepared records alone. Restart includes prepared records in the new work. Either action leaves a dataset alone while it is running. A request finishes when every dataset it names is prepared or shelved. If it stops waiting for intervention, its detail page lists which records still need work. Check again checks their state without starting a fresh preparation round.

Resume keeps a stopped dataset round's existing results and the versions of the catalog, reader and harness that it pinned. The harness is the shared software that opens images and checks or produces crops. Keeping a pin means keeping the exact code version, not just its name. Resume continues at the first unfinished step. Restart starts a new dataset round with current versions of the catalog, readers and harness. Restart is appropriate when a fix requires newer code or catalog data. After a force stop, the workflow's in-memory results are lost, so a resume starts from the beginning.

Review crops

Preparation makes example crops so that image content, channels and labels can be inspected. A label is an annotation such as a mask marking individual cells. The dataset page shows its progress, evidence and timeline. If a person is asked to review, the verdict applies to the displayed crop set. Approval saves the reviewed crops. Rejection sends feedback for rework. A saved crop set can also be rejected later, which withdraws it and starts rework.

The crop judge depends on the installation's settings. When off, it does not run. In shadow mode it records an assessment without deciding. In active mode it can approve a crop set or send concerns back for rework, with a limit on automatic reworks. An uncertain case goes to a person. A person's verdict takes precedence over the judge's assessment of the same crop set.

Some sources need a new or corrected reader. The system can ask the autodev workflow to propose changes in the snippets repository. It may still need a person to review or resolve a problem. The dataset timeline explains what is waiting.

What evidence merits approval?

A file that opens without error can still produce misleading data. The reviewer compares the gallery with the catalog description. Is an apparent channel actually a time point? Does a label outline coincide with its structure in the image? A useful rejection identifies the crop set, the affected example and the mismatch. This gives the reader developer a testable observation rather than a general request for better crops. The Decisions tab brings together assessments, including comparisons where the judge and a person inspected the same crop set.

3. Define a buffer

Why a buffer definition is needed

Different experiments need different data. The buffer definition makes the selection and sampling choices explicit, so that the user can inspect the buffer plan and link a training run to a specific buffer version. The New buffer button opens an unsaved draft.

The controls and YAML tabs edit the same buffer definition. Controls cover common choices. YAML is the text format for these settings. Indentation groups related settings together. YAML also supports choices that the controls cannot express. If the YAML contains such a choice, it remains the source of truth and the controls become read-only until it is removed.

  • Selection narrows the catalog by properties such as the number of image dimensions, the imaging method (modality), the licence and whether annotations are available. Individual records can be excluded.
  • Patch and levels. The patch size sets the crop dimensions in pixels at each resolution. The levels set the resolutions to sample around the same centre.
  • Weighting and crop count determine how the pool is distributed across datasets. Weighting can balance modalities rather than simply favoring the largest datasets.
  • Splits are the portions of the data reserved for training, validation and testing. Normalization and channels describe how samples are presented.
  • Filters, when configured, test candidate crops for requested content or labels. A source can yield fewer crops than planned when suitable crops cannot be found.

The preview summarizes matches, prepared datasets and weight shares. The Where datasets leave counts separate three reasons a candidate can disappear: it fails a selection rule, its images cannot supply the requested field of view, or it fits but has not been prepared. The incomplete records view identifies missing catalog information. Unchecking a matching dataset adds its ID to the buffer definition’s exclusions without changing the catalog. Records missing information needed for planning are counted and can be inspected on the Datasets tab. Save buffer and continue gives the buffer a page. Saving does not start buffer planning.

A worked experiment: cell detail in its tissue context

Consider a lab training on single-channel, two-dimensional images. A small patch shows fine structure, but a model may also need the surrounding tissue. The lab chooses 256 × 256 pixels at three levels. Level 1 shows the detail. Levels 2 and 4 cover a wider area around the same centre without increasing the input dimensions.

How the choices translate to YAML

The page supplies the catalog repository and commit. The example below shows the selection, sampling and split sections of the buffer definition, not a standalone file. It admits annotated 2D records under the listed licences. It does not require every crop to contain a label. 

select:
  where:
    dims: {in: [2D]}
    license: {in: [CC0-1.0, CC-BY-4.0], allow_unknown: false}
    annotations: {required: true}
sampling:
  patch: {2D: {y: 256, x: 256}, c: 1}
  levels: [1, 2, 4]
  crops: {train: 4000, val: 200, test: 200}
  max_crops_per_dataset: 1024
  weighting: {scheme: temperature, over: [modality, dataset], temperature: 0.5}
splits:
  fractions: {train: 0.8, val: 0.1, test: 0.1}
  seed: 7

Weights answer a different question from splits. A split reserves material for a purpose. A weight describes how often a source should contribute. With the grouping above, temperature zero gives modalities equal shares and divides each share equally among its datasets. At one, shares follow estimated capacity. The intermediate setting tempers the influence of large sources. The ordinary fractional split assigns planes, not whole datasets. Related planes from the same acquisition can therefore appear in different splits. To reserve an entire dataset for an independent test, its record ID belongs in splits.holdout_ids.

Count is a target, not an inventory. A record with a 3% share of 4,000 training crops has a target of 120. The planner rounds that to 128 before applying the per-dataset cap. Rounding lets small changes in a pool reuse the same staged data. The Source table reports what was actually staged.

When the experiment needs labelled pixels

Requiring annotations in the catalog admits datasets that report having labels. It says nothing about a particular field of view. For an experiment where a blank mask is uninformative, the following optional part of sampling asks the stage job to check each candidate: 

filters:
  - {name: content}
  - {name: labelled}

The content check rejects blank or constant images. The labelled check requires annotation in the crop itself: one annotated pixel is enough, so a point or a thin outline counts. It looks at the whole area the crop covers at its coarsest level, so the finest level of a crop may hold none. A source with no label array has none, so a dataset whose annotations are only per image (a class, a count) is left out of the plan under this filter, with that reason. A filter may leave a dataset with fewer samples. It does not make another dataset contribute the missing samples.

4. Prepare datasets and review the buffer plan

The Prepare step lists matching datasets and their preparation stages. A buffer only plans over datasets that are prepared when the buffer round starts. The user can select matching records and choose Resume or Restart to file a preparation request. Continue with N prepared datasets starts the buffer round with the prepared records already available. Datasets prepared later can be included in a future buffer plan.

The resulting buffer plan shows which datasets were selected, their weights and their planned crops. For example, a 10% test fraction does not guarantee that a small volume supplies a test plane. Reserving a whole dataset for testing keeps its images out of training. No source data is staged during planning. At this point the user can check which datasets have the largest sampling weights and how many crops are planned for each split before choosing Run: stage. The page also presents any hosts that require approval for the staging jobs. Approval is a security decision about the hosts those jobs may contact.

To edit the buffer definition after reviewing the buffer plan, the user cancels the buffer round. A serving buffer’s definition is fixed, but Clone starts a new buffer from a copy.

5. Stage and serve

What staging does

Staging makes the planned samples available on shared storage. Each job reads the source regions needed by the planned samples and writes a pyramid for each volume. A pyramid stores the same image at several resolutions. Staging keeps only the image chunks needed for the planned crops rather than downloading the entire dataset in advance. A cache is a copy kept on disk so later jobs can reuse it. When a reader must take a file whole, that file is kept in the shared raw cache. Transfer limits, source access and available cache space still matter.

The Source step shows progress and failures by dataset. A dataset is servable when its staged samples are available to the buffer. At staged, the table lists the datasets available for training and the volume counts for each split. Approve and serve accepts that buffer version, including any shortfall shown at approval. The buffer definition can request automatic approval as described below.

Some sources require files to be placed by hand. When the page asks for them, follow the timeline's instructions and select Files are in place after copying finishes. A job can also wait for cache space or another job's lock. A wait for space means the shared cache is over its quota. A lock wait means a different job has exclusive write access to this record. Neither is a reason to start a second preparation round.

ready.min_fraction is the fraction of datasets that must be servable in each group. Dropped records are left out of the denominator. This fraction is not a sampling weight or a count of patches. With plan.auto_approve enabled, the staged buffer version can serve automatically when every group reaches the threshold. This setting is distinct from accepting the buffer plan on the Plan step. Without automatic approval, the staged buffer version waits for a decision even when coverage is complete. A dataset still waiting on files can join after approval. A failed dataset does not join merely because the buffer version was approved.

Use a buffer version

The Serve step lists the included datasets and the buffer version ID to use in training. That ID identifies the buffer plan the training job requests. It is not a record of the individual samples the job received.

When another dataset becomes available

Suppose a training job uses a buffer version built from five prepared datasets. If a sixth matching dataset becomes prepared later, it does not join the existing buffer plan. The user can select Plan a new version to include it. Once the new buffer version is approved, training code can request its ID. The running job continues to request the original buffer version ID.

Keeping the same buffer version ID does not guarantee that every planned dataset is always available. A dataset already in the buffer plan can start serving once its samples are staged or stop serving if it is revoked. If the original buffer version is retired, requests for its ID fail instead of switching to the new one.

6. Use a buffer in training

The training process needs access to buffer-api, the shared staged storage and the mia-snippets harness environment. The example uses the buffer version ID shown on the Serve step. It assumes PyTorch and the harness are installed and this repository is on the Python path. 

from torch.utils.data import DataLoader
from mia_buffers.client import BufferDataset

train = BufferDataset(
    "<service URL>", "<buffer version ID>", "train",
    n_samples=4000, tensorizers="<mia-snippets checkout>",
)
validation = BufferDataset(
    "<service URL>", "<buffer version ID>", "val",
    tensorizers="<mia-snippets checkout>",
)
loader = DataLoader(train, batch_size=32, num_workers=8,
                    collate_fn=BufferDataset.collate)
batch = next(iter(loader))
print(batch["img"].shape)
print(batch["bbox"].shape)

Training draws are weighted samples with replacement. n_samples sets the length of a virtual training epoch. Validation and test use frozen sample lists. The service supplies descriptions of samples rather than image pixels. The training process reads the staged data locally and converts each sample into tensors, the numerical arrays handed to the model.

Read the first batch

The collate function combines individual samples into a batch. This one keeps the keys common to the samples in a batch. A label layer present in only some samples is not a shared batch target. For the worked example, a single image tensor has shape (3, 1, 256, 256): levels, channels, height and width. For a full batch the printed image shape is (32, 3, 1, 256, 256). The bounding boxes have shape (32, 3, 2, 2): two corners with two coordinates at each level. They locate each field in physical space. Per-sample metadata stays in a list rather than being forced into a common tensor.

A commit identifies an exact revision of code. The buffer version records the harness commit. The client checks that its copy of the harness matches that commit. For a reproducible run, the training environment should use the matching checkout. Record the buffer version ID and harness commit with the experiment. The buffer version detail page reports consumers and usage, which makes it possible to check which buffer version the job actually drew from. Training jobs cannot draw from an unapproved or retired buffer version.

7. Follow work and manage its lifetime

Each dataset, request and buffer has a stage and a timeline. The stage describes where the work is. The timeline explains what happened and links to job records when available. Overview separates work in progress, work in repair and work with the status needs human.

Shelve sets aside a subject with a reason when no round is open. A shelved dataset is not selected for buffer plans or started by preparation requests. Unshelve makes it available again. A dataset waiting for review is cancelled before it is shelved.

In Needs human, the most recent timeline entry explains the decision. Cancel the round asks a running workflow to stop. Force stop is a last resort for a workflow that does not answer cancellation. It terminates the workflow but does not itself kill a running cluster job. By default a serving buffer becomes idle after 72 hours without use. After another 14 idle days it is eligible for retirement. The buffer definition sets both intervals. The buffer page lists buffer versions and their usage.

Choose the action at the right scope

IntentAction and consequence
Set aside a record without judging its quality.Shelve records a reason. A preparation request can finish without that record. Unshelving does not prepare it.
Correct a reader error found after review.Reject on the dataset identifies the saved crop set, withdraws it and starts rework. A new verdict must name the new crop set.
Remove a source from this serving buffer version.Revoke under Included datasets withdraws the selected records. Inspect the remaining group coverage before training on the remaining datasets.
Use additional prepared datasets with the same buffer definition.Plan a new version creates a new buffer plan. Training does not switch IDs automatically. To change the selection rules instead, the user clones the buffer definition.
Finish an experiment.Retire closes every version of the buffer to training jobs and releases their storage references. It works from any state: a round in progress is cancelled first, and a buffer with nothing to release is simply marked retired. It does not delete files still shared with other buffers.
